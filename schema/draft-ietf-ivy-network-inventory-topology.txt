<h1 id="title">A YANG Network Data Model for Inventory Topology Mapping</h1>
<section id="section-abstract">
      <h2 id="abstract"><a href="#abstract" class="selfRef">Abstract</a></h2>
<p id="section-abstract-1">This document defines a YANG data model that extends the network
topology data model (RFC 8345) to map network topologies with inventories. The data model
introduces the "inventory-topology" network type and augmentations
for physical entity mappings and capabilities, which may be used by
any overlay network topology for service provisioning validation,
network maintenance, and capacity planning.<a href="#section-abstract-1" class="pilcrow">¶</a></p>
</section>
<section class="note rfcEditorRemove" id="section-note.1">
      <h2 id="name-discussion-venues">

<div id="introduction">
<section id="section-1">
      <h2 id="name-introduction">
<a href="#section-1" class="section-number selfRef">1. </a><a href="#name-introduction" class="section-name selfRef">Introduction</a>
      </h2>
<p id="section-1-1"><span>[<a href="#I-D.ietf-ivy-network-inventory-yang" class="cite xref">I-D.ietf-ivy-network-inventory-yang</a>]</span> defines the base network inventory
  model to aggregate the inventory data of Network Elements (NEs). This data includes identification of these NEs and their hardware,
  firmware, and software components.  Examples
   of inventory hardware components could be rack, shelf, slot, board,
   or physical port.  Examples of inventory software components could
   be platform Operating System (OS), software-modules, bios, or boot-loader <span>[<a href="#I-D.ietf-ivy-network-inventory-software" class="cite xref">I-D.ietf-ivy-network-inventory-software</a>]</span>.<a href="#section-1-1" class="pilcrow">¶</a></p>
<p id="section-1-2">In order to ease navigation between inventory and network topologies,
this document extends the network topology data model <span>[<a href="#RFC8345" class="cite xref">RFC8345</a>]</span> for network
inventory mapping: "ietf-network-inventory-topology" (<a href="#sec-module" class="auto internal xref">Section 5</a>).<a href="#section-1-2" class="pilcrow">¶</a></p>
<p id="section-1-3">Similar to the base inventory data model  <span>[<a href="#I-D.ietf-ivy-network-inventory-yang" class="cite xref">I-D.ietf-ivy-network-inventory-yang</a>]</span>, the network inventory topology
does not make any assumption about involved NEs and their roles in topologies. As such, the mapping
data model can be applied independent of the network type (optical local loops, access network, core network, etc.) and application.<a href="#section-1-3" class="pilcrow">¶</a></p>
<p id="section-1-4">Therefore, this YANG data model can be used to represent a physical network instance at the lowest underlay abstraction level, as shown in <span><a href="https://rfc-editor.org/rfc/rfc8345#section-4.4.9" class="relref">Section 4.4.9</a> of [<a href="#RFC8345" class="cite xref">RFC8345</a>]</span>.
Alternatively, it can be used in conjunction with existing network topology
models, such as <span>[<a href="#RFC9408" class="cite xref">RFC9408</a>]</span>, <span>[<a href="#RFC8944" class="cite xref">RFC8944</a>]</span>, <span>[<a href="#RFC8346" class="cite xref">RFC8346</a>]</span>, <span>[<a href="#RFC8795" class="cite xref">RFC8795</a>]</span>, and
<span>[<a href="#I-D.ietf-ccamp-otn-topo-yang" class="cite xref">I-D.ietf-ccamp-otn-topo-yang</a>]</span>, when they contain nodes, links,
or termination points belonging to the lowest underlay level.<a href="#section-1-4" class="pilcrow">¶</a></p>

<section id="section-3">

<a href="#section-3" class="section-number selfRef">3. </a><a href="#name-sample-use-cases-of-the-dat" class="section-name selfRef">Sample Use Cases of the Data Model</a>
      </h2>
<div id="determine-available-resources-of-service-attachment-points-saps">
<section id="section-3.1">
        <h3 id="name-determine-available-resourc">
<a href="#section-3.1" class="section-number selfRef">3.1. </a><a href="#name-determine-available-resourc" class="section-name selfRef">Determine Available Resources of Service Attachment Points (SAPs)</a>
        </h3>
<p id="section-3.1-1">The inventory topology data model provides a physical port
reference (port-ref) that enables correlation between logical
topology entities and physical inventory components.  During
service provisioning, the SAP's parent-termination-point can be
associated with the inventory topology's port-ref to locate the
underlying physical resource.<a href="#section-3.1-1" class="pilcrow">¶</a></p>
<p id="section-3.1-2"><a href="#nwi-topology-usage" class="auto internal xref">Figure 1</a> illustrates the query interactions.
During service provisioning, the orchestrator can issue a query using the SAP
data model (e.g., obtaining a list of SAPs across multiple PEs
as shown in <span><a href="https://rfc-editor.org/rfc/rfc9408#appendix-A" class="relref">Appendix A</a> of [<a href="#RFC9408" class="cite xref">RFC9408</a>]</span>), and then uses the
inventory topology data model to identify the physical port underlying each
candidate SAP. Specifically, the "parent-termination-point"
of a SAP is mapped to the corresponding "port-ref"
in the inventory topology, allowing the orchestrator to locate the
physical resource. The orchestrator can then consult other relevant
topology models (e.g., <span>[<a href="#RFC8795" class="cite xref">RFC8795</a>]</span>) to verify whether the identified
port has adequate capacity for the requested service.<a href="#section-3.1-2" class="pilcrow">¶</a></p>
<p id="section-3.1-3">If the physical port underlying a candidate SAP has insufficient
resources (e.g., port speed fully utilized), the orchestrator
can select an alternate SAP that maps to a different port
with adequate capacity.  If no alternative SAP is available,
the orchestrator flags the request for manual intervention,
providing the operator with precise inventory information
about the bottleneck (e.g., "Port GE0/6/1 on NE-PE1 is at 95% utilization").
The resource constraint can also feed into a "what-if" analysis
(see <a href="#sec-whatif" class="auto internal xref">Section 3.3</a>) to evaluate hardware upgrades or
alternative underlay paths.<a href="#section-3.1-3" class="pilcrow">¶</a></p>

<section id="section-3.2">
        <h3 id="name-multi-layer-network-navigat">
<a href="#section-3.2" class="section-number selfRef">3.2. </a><a href="#name-multi-layer-network-navigat" class="section-name selfRef">Multi-layer Network Navigation</a>
        </h3>
<p id="section-3.2-1">A multi-layer network encompasses multiple layers (e.g., Layer 2 and Layer 3, or Optical Transport Network (OTN) and Wavelength Division Multiplexing (WDM) layers).<a href="#section-3.2-1" class="pilcrow">¶</a></p>
<p id="section-3.2-2">A multi-layer network topology comprises nodes, links, and termination points that can belong to different layers.<a href="#section-3.2-2" class="pilcrow">¶</a></p>
<p id="section-3.2-3">A multi-layer network can contain multiple types of topological elements: physical elements (associated with an inventory element) or logical elements (associated with topology elements in the underlay layer).<a href="#section-3.2-3" class="pilcrow">¶</a></p>
<p id="section-3.2-4">The topology models support navigation across the different layers, down to the physical layer, as defined in <span><a href="https://rfc-editor.org/rfc/rfc8345#section-4.4.9" class="relref">Section 4.4.9</a> of [<a href="#RFC8345" class="cite xref">RFC8345</a>]</span>. The navigation between the physical layer and the network inventory is outside the scope of the topology models and is addressed in this document.<a href="#section-3.2-4" class="pilcrow">¶</a></p>
</section>
</div>
<div id="sec-whatif">
<section id="section-3.3">
        <h3 id="name-what-if-scenarios">
<a href="#section-3.3" class="section-number selfRef">3.3. </a><a href="#name-what-if-scenarios" class="section-name selfRef">"What-if" Scenarios</a>
        </h3>
<p id="section-3.3-1"><span>[<a href="#I-D.irtf-nmrg-network-digital-twin-arch" class="cite xref">I-D.irtf-nmrg-network-digital-twin-arch</a>]</span> defines Network Digital Twin (NDT)
   as a virtual representation of the physical network.  Such
    representation is meant to be used to analyze,
   diagnose, emulate, and then manage the physical network based on
   data, models, and interfaces.<a href="#section-3.3-1" class="pilcrow">¶</a></p>
<p id="section-3.3-2"><span>[<a href="#I-D.ietf-nmop-simap-concept" class="cite xref">I-D.ietf-nmop-simap-concept</a>]</span> defines Service and Infrastructure Maps (SIMAP)
 as an abstraction model that provides a unified view of both service and
 infrastructure information, enabling correlation between service requirements
 and underlying resource capabilities.<a href="#section-3.3-2" class="pilcrow">¶</a></p>
<p id="section-3.3-3">Both architectures require accurate mapping between logical network topology
 and physical inventory as a foundational data layer. This model provides
 the essential physical resource information to such systems, enabling
 them to perform accurate "what-if" analysis (e.g., impact prediction
 of hardware End-of-Life, path re-optimization under resource constraints, service
 availability assessment).<a href="#section-3.3-3" class="pilcrow">¶</a></p>

<div id="port-breakout-capability">
<section id="section-4.2">
        <h3 id="name-port-breakout-capability">
<a href="#section-4.2" class="section-number selfRef">4.2. </a><a href="#name-port-breakout-capability" class="section-name selfRef">Port-Breakout Capability</a>
        </h3>
<p id="section-4.2-1">High-density Ethernet ports (e.g., 400 Gb/s DR4) can be split into
multiple independent lower-speed channels. The breakout channels
represent the intrinsic capability of the port to be partitioned,
regardless of whether the port is currently configured as a trunk or as
a breakout port.<a href="#section-4.2-1" class="pilcrow">¶</a></p>
<p id="section-4.2-2">A trunk port is associated with exactly one physical interface.
A breakout port is a port that is decomposed into two or more physical
interfaces; those interfaces may run at the same or different speeds
and may consume the same or a different number of breakout channels.<a href="#section-4.2-2" class="pilcrow">¶</a></p>
<p id="section-4.2-3">The container "port-breakout" is added under the termination-point
augmentation.  It lists the logical channels into which the single
physical port can be divided.  Only termination-points whose parent
port is breakout-capable need to instantiate the container; otherwise
the container is omitted, keeping the topology model minimal for the
common non-breakout case.<a href="#section-4.2-3" class="pilcrow">¶</a></p>
<p id="section-4.2-4">Breakout channel is an atomic resource element obtained by partitioning a breakout port.
One physical interface may be associated with one or more breakout
channels, but one breakout channel MUST NOT be associated with more
than one physical interface. Appendix B provides example configurations.<a href="#section-4.2-4" class="pilcrow">¶</a></p>
<p id="section-4.2-5">It is assumed that a port which supports breakout can be configured
either as a trunk port or as a breakout port. Interface channelisation (e.g., VLAN sub-interfaces) is
outside the scope of this document and is addressed by the Layer 2 network topology model <span>[<a href="#RFC8944" class="cite xref">RFC8944</a>]</span>.<a href="#section-4.2-5" class="pilcrow">¶</a></p>
</section>

<section id="section-6">
      <h2 id="name-operational-considerations">
<a href="#section-6" class="section-number selfRef">6. </a><a href="#name-operational-considerations" class="section-name selfRef">Operational Considerations</a>
      </h2>
<p id="section-6-1">This model enables a network controller to report discovered network topology and inventory information. Automatic discovery serves as the primary mechanism, with selective configuration capabilities provided for scenarios where discovery is not feasible.<a href="#section-6-1" class="pilcrow">¶</a></p>
<p id="section-6-2">For typical operations such as service provisioning and network planning, the model offers read-only query
access to authoritative mappings between logical topology and physical inventory.
The inventory-mapping-attributes containers are defined as read-write (config true) to accommodate cases where automatic discovery is not possible, including:<a href="#section-6-2" class="pilcrow">¶</a></p>
<ul class="normal">
<li class="normal" id="section-6-3.1">
          <p id="section-6-3.1.1">Customer-premises equipment (CPE) outside the operator's management domain<a href="#section-6-3.1.1" class="pilcrow">¶</a></p>
</li>
        <li class="normal" id="section-6-3.2">
          <p id="section-6-3.2.1">Leased lines and third-party transport resources<a href="#section-6-3.2.1" class="pilcrow">¶</a></p>
</li>
        <li class="normal" id="section-6-3.3">
          <p id="section-6-3.3.1">Planned or hypothetical resources for future deployment<a href="#section-6-3.3.1" class="pilcrow">¶</a></p>
</li>
      </ul>
<p id="section-6-4">In these cases, the operator manually configures the mapping to maintain accurate topology-to-inventory correlation.<a href="#section-6-4" class="pilcrow">¶</a></p>
<p id="section-6-5">The following nodes are read-only (config false) as they represent hardware-determined state:<a href="#section-6-5" class="pilcrow">¶</a></p>
<span class="break"></span><dl class="dlParallel" id="section-6-6">
        <dt id="section-6-6.1">port-breakout:</dt>
        <dd style="margin-left: 1.5em" id="section-6-6.2">
          <p id="section-6-6.2.1">Hardware capability determined by physical port characteristics<a href="#section-6-6.2.1" class="pilcrow">¶</a></p>
</dd>
      <dd class="break"></dd>
</dl>
</section>

<div id="security-considerations">
<section id="section-7">
      <h2 id="name-security-considerations">
<a href="#section-7" class="section-number selfRef">7. </a><a href="#name-security-considerations" class="section-name selfRef">Security Considerations</a>
      </h2>
<p id="section-7-1">This section is modeled after the template described in <span><a href="https://rfc-editor.org/rfc/rfc9907#section-3.7.1" class="relref">Section 3.7.1</a> of [<a href="#RFC9907" class="cite xref">RFC9907</a>]</span>.<a href="#section-7-1" class="pilcrow">¶</a></p>
<p id="section-7-2">The "ietf-network-inventory-topology" YANG module defines a data model that is
designed to be accessed via YANG-based management protocols, such as
Network Configuration (NETCONF) <span>[<a href="#RFC6241" class="cite xref">RFC6241</a>]</span> and RESTCONF <span>[<a href="#RFC8040" class="cite xref">RFC8040</a>]</span>. These YANG-based management (1) have to
use a secure transport layer (e.g., Secure Shell (SSH) <span>[<a href="#RFC4252" class="cite xref">RFC4252</a>]</span>, TLS <span>[<a href="#I-D.ietf-tls-rfc8446bis" class="cite xref">I-D.ietf-tls-rfc8446bis</a>]</span>, and
QUIC {{?RFC9000]) and (2) have to use mutual authentication.<a href="#section-7-2" class="pilcrow">¶</a></p>
<p id="section-7-3">The Network Configuration Access Control Model (NACM) <span>[<a href="#RFC8341" class="cite xref">RFC8341</a>]</span>
provides the means to restrict access for particular NETCONF or
RESTCONF users to a preconfigured subset of all available NETCONF or
RESTCONF protocol operations and content.<a href="#section-7-3" class="pilcrow">¶</a></p>
<p id="section-7-4">There are a number of data nodes defined in this YANG module that are
   writable/creatable/deletable (i.e., "config true", which is the
   default).  All writable data nodes are likely to be sensitive or
   vulnerable in some network environments.  Write
   operations (e.g., edit-config) and delete operations to these data
   nodes without proper protection or authentication can have a negative
   effect on network operations.  The following subtrees and data nodes
   have particular sensitivities/vulnerabilities:<a href="#section-7-4" class="pilcrow">¶</a></p>
<p id="section-7-5">'ne-ref', 'port-ref', 'link-type':
  These nodes are sensitive as they establish the mapping
  between logical topology and physical inventory. Unauthorized
  modification could lead to incorrect resource allocation or
  service disruption.<a href="#section-7-5" class="pilcrow">¶</a></p>
<p id="section-7-6">Some of the readable data nodes in this YANG module may be considered
sensitive or vulnerable in some network environments.  It is thus
important to control read access (e.g., via get, get-config, or
notification) to these data nodes. Specifically, the following
subtrees and data nodes have particular sensitivities/
vulnerabilities:<a href="#section-7-6" class="pilcrow">¶</a></p>
<p id="section-7-7">'ne-ref':
   The references may be used to track the set of network elements. While
   read-only, they may reveal network infrastructure details.<a href="#section-7-7" class="pilcrow">¶</a></p>
<p id="section-7-8">'port-breakout':
   This node exposes hardware capabilities.<a href="#section-7-8" class="pilcrow">¶</a></p>

<section id="appendix-B">
      <h2 id="name-json-example-of-an-multi-fi">
<a href="#appendix-B" class="section-number selfRef">Appendix B. </a><a href="#name-json-example-of-an-multi-fi" class="section-name selfRef">JSON Example of an Multi-fibre Push On (MPO) Breakout-Channel Port</a>
      </h2>
<p id="appendix-B-1">This appendix provides an example of a 400 Gb/s DR4 port that is physically implemented as four independent 100 Gb/s lanes (an MPO breakout). The lanes are exposed as breakout-channel entries so that the port can later be configured as either a single 400G trunk or four 100G breakout interfaces. The instance data below shows the minimal JSON encoding <span>[<a href="#RFC7951" class="cite xref">RFC7951</a>]</span> of the "port-breakout" container for this port.<a href="#appendix-B-1" class="pilcrow">¶</a></p>
<div class="lang-json sourcecode" id="appendix-B-2">
<pre>
=============== NOTE: '\' line wrapping per RFC 8792 ================

{
  "ietf-network-topology:networks": {
    "network": [
      {
        "network-id": "example:underlay-topology-400g",
